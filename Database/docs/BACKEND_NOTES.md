# Backend notları (Spring Boot 4.1.1 / Java 21 / JPA-Hibernate)

Bu şema Hibernate'in kolay eşleyeceği şekilde tasarlandı. Aşağıdakiler backend yazarken işinize yarayacak notlar.

> `Graduate Project/DiaMate/pom.xml` Spring Boot **4.1.1** ve **Java 21** kullanıyor (proje raporundaki 3.1 / Java 17'den farklı; sorun değil, bu şema ikisiyle de çalışır). Veritabanı ve güvenlik bağımlılıkları (`spring-boot-starter-data-jpa`, `postgresql`, `spring-boot-starter-validation`, `spring-boot-starter-security-oauth2-resource-server`) eklendi.

## 1. Bağlantı

Backend, bu paketin kurulduğu **Docker veritabanına** bağlanır: `localhost:5434`, veritabanı `diamate` (bkz. `../README.md`). pgAdmin'deki 5433 sunucusu yalnızca referanstır.

`DiaMate/src/main/resources/application.yml` içindeki güncel hali (değerler `DiaMate/.env` dosyasından okunur):

```yaml
spring:
  config:
    import: optional:file:.env[.properties]
  datasource:
    url: jdbc:postgresql://${POSTGRES_HOST:localhost}:${POSTGRES_PORT:5434}/${POSTGRES_DB:diamate}
    username: ${POSTGRES_USER}       # geliştirmede: diamate (Docker konteynerinin kullanıcısı)
    password: ${POSTGRES_PASSWORD}   # şifre koda/yml'e yazılmaz, .env'den gelir
  jpa:
    hibernate:
      ddl-auto: validate             # ASLA update/create: şemayı bu SQL dosyaları yönetir
    open-in-view: false
    properties:
      hibernate:
        jdbc.time_zone: UTC
```

> Geliştirmede backend Docker'daki `diamate` kullanıcısıyla (süper kullanıcı) bağlanıyor. Üretimde en az yetki ilkesiyle `diamate_app` rolü kullanılmalı: `ALTER ROLE diamate_app LOGIN PASSWORD '...';` ve `.env`'de `POSTGRES_USER=diamate_app`.

Şema `public`; `default_schema` ayarı gerekmez. Yalnız `diamate_app` yetkileri: `public` tablolarında SELECT/INSERT/UPDATE/DELETE (`audit_logs` hariç: yalnız SELECT/INSERT), `research` şemasında yalnız SELECT.

## 2. Tür eşlemesi

| PostgreSQL | Java |
|---|---|
| `bigint GENERATED BY DEFAULT AS IDENTITY` | `Long` + `@GeneratedValue(strategy = GenerationType.IDENTITY)` |
| `timestamptz` | `java.time.Instant` (ya da `OffsetDateTime`) |
| `date` / `time` | `LocalDate` / `LocalTime` |
| `numeric(p,s)` | `BigDecimal` |
| `uuid` (`client_uuid`) | `java.util.UUID` |
| `jsonb` (`reports.summary`, `audit_logs.details`) | `@JdbcTypeCode(SqlTypes.JSON)` + `Map<String,Object>` |
| `varchar` + `CHECK (... IN (...))` | Java `enum` + `@Enumerated(EnumType.STRING)`; enum sabitleri CHECK listesiyle birebir aynı olmalı (sözlükte yazılı) |
| `boolean` | `boolean` / `Boolean` |

- `patient_profiles.user_id` ve `clinician_profiles.user_id` hem birincil anahtar hem `users.id` yabancı anahtarı: `@OneToOne @MapsId`.
- `users` bir PostgreSQL ayrılmış sözcüğü değil ama `user` öyledir. Tablo adı zaten `users`, `@Table(name = "users")` yeterli.
- `updated_at`: veritabanı trigger'ı her UPDATE'te kendisi günceller. Entity'de `@Column(insertable = false, updatable = false)` yapın ya da bırakın, çakışma olmaz.

## 3. Soft delete ve çevrimdışı senkronizasyon

- Günlük tablolarında (`glucose_logs`, `meal_logs`, `insulin_logs`, `activity_logs`, `symptom_logs`, `medication_intakes`) `deleted_at` var. `@SQLRestriction("deleted_at IS NULL")` (Hibernate 6.3'ten beri `@Where` yerine önerilen yol). Silme = `deleted_at = now()`.
- Mobil uygulama her kayda bir `client_uuid` üretir. `(patient_id, client_uuid)` benzersizdir: aynı istek iki kez gelirse `INSERT ... ON CONFLICT (patient_id, client_uuid) WHERE client_uuid IS NOT NULL DO UPDATE` ile (native query) idempotent çalışır. Çakışmada kural rapordaki gibi son yazan kazanır (`updated_at`).
- Kullanıcıları asla fiziksel silmeyin: `users.is_active = false`. (Fiziksel silme hastanın tüm verisini zincirleme siler.)

## 4. Kimlik doğrulama

- `users.password_hash` **bcrypt** (`$2a$10$…`). `BCryptPasswordEncoder` doğrudan doğrular. Yeni kayıtta backend `encoder.encode(...)` ile yazar (veritabanı hiçbir zaman düz şifre görmez).
- Rol → `GrantedAuthority`: `"ROLE_" + users.role` (PATIENT, CLINICIAN, CAREGIVER, ADMIN).
- Hesap kilitleme için `failed_login_attempts` ve `locked_until`, 2FA için `two_factor_enabled` / `two_factor_secret` (TOTP sırrını uygulama şifreleyerek yazsın).
- `refresh_tokens.token_hash` ve `password_reset_tokens.token_hash`: token'ın **özetini** saklayın (SHA-256), kendisini değil.
- Demo giriş: `patient01@diamate.example` / `DiaMate!2026` (bkz. DEMO_ACCOUNTS.md).

## 5. Yetkilendirme (rapordaki "paylaşım" akışı)

- Hasta kendi verisini her zaman görür. Doktor/bakıcı yalnızca `care_relationships.status = 'ACTIVE'` (ve süresi geçmemiş) satırı ve ilgili izin bayrağıyla görür: `can_view_glucose`, `can_view_meals`, `can_view_medications`, `can_view_activity`, `can_view_reports`, `can_receive_alerts`, `can_add_recommendations`.
- Veritabanında hazır fonksiyon: `SELECT fn_can_access(:viewerId, :patientId, 'glucose')` (izin adları: glucose, meals, medications, activity, reports, alerts, recommend). Servis katmanında aynı mantığı Java'da da yazabilirsiniz, ama iki yerde tutarsızlık olmasın.
- **ADMIN sağlık verisine erişemez.** Bu bilinçli: yönetici hesap yönetir, hasta verisi görmez.
- Paylaşım: `POST /share` → `care_relationships` satırı `PENDING`; hasta onaylayınca `ACTIVE`; `DELETE /revoke` → `REVOKED` (`revoked_at` trigger ile dolar).
- Her veri erişimini `audit_logs`'a yazın (`VIEW_PATIENT_DATA`, `LOGIN`, `LOGIN_FAILED`, `SHARE_GRANTED`, `EXPORT_REPORT`, …). Tablo yalnızca eklenir, `diamate_app` rolü UPDATE/DELETE yapamaz.

## 6. İş mantığı backend'de kalır (veritabanı yalnız yardımcı sağlar)

| İş | Nasıl |
|---|---|
| Uyarı üretimi | Yeni glukoz kaydında `SELECT fn_glucose_alert_type(:patientId, :value)` → `URGENT_LOW / LOW / HIGH / URGENT_HIGH / NULL`; `alerts` ve `notifications` satırı yaz. Eşikler `patient_profiles` içinde hasta bazlıdır. |
| Hatırlatıcı | `reminders` tanımı; bir zamanlayıcı (`@Scheduled`) `reminder_events` satırlarını üretir (`PENDING → SENT → TAKEN / MISSED`), kaçırılanı `missed_count`'a ve gerekirse `alerts.MISSED_DOSE`'a yansıtır. Uyum: `v_reminder_adherence_30d`. |
| Bildirim | `notifications` + `device_tokens` (FCM). Durum `PENDING → SENT / FAILED / READ`. |
| Rapor | Sayılar için `fn_glucose_summary(:patientId, :from, :to)` (jsonb: ortalama, SD, CV, GMI, TIR/TBR/TAR); sonucu `reports.summary`'ye, PDF yolunu `file_path`'e yazın. |
| CSV içe aktarma | `csv_imports` iş kaydı, satırlar `glucose_logs`'a `source = 'CSV_IMPORT'` ile. |
| Yapay zekâ asistanı (Dia) | Konuşma `ai_conversations` / `ai_messages`; asistan bir kayıt oluşturduysa `created_entity_type` + `created_entity_id`. |
| Öğün fotoğrafı | Model çıktısı `food_catalog.research_class_id` (Food-101 sınıf numarası, 1–101, ada göre sıralı) ile eşleşir; `meal_logs.source = 'AI_PHOTO'`, `ai_confidence` 0–1. |

## 7. Performans

- `glucose_logs` (ve `wearable_samples`) büyür: CGM 5 dakikada bir okuma, hasta başına yılda ~100 bin satır. Her zaman **`patient_id` + `measurement_time` aralığı** ile sorgulayın (indeks bunun için: `ix_glucose_logs_patient_time`) ve sayfalayın. Grafik için `v_glucose_daily` gün özeti, saatlik/ham için tabloyu zaman aralığıyla sorgulayın.
- `v_glucose_daily`, `v_glucose_14d`, `v_logbook` view'larını **hep `patient_id` ile** filtreleyin. `v_glucose_daily` içinde `day` filtresi indeks kullanmaz, indeksi `patient_id` kullanır; çok uzun geçmişte zaman aralığını taban tabloya yazın.
- `research.*` tablolarında `SELECT *` yapmayın (`glucose_readings` 648 bin, `activity` 547 bin, `timeline` 703 bin, `brfss_survey` 254 bin satır).
- Pool: HikariCP varsayılanı yeterli.

## 8. Yapay zekâ servisi (Dia, FastAPI) ve analiz

- `diamate_readonly` rolü tüm tabloları okuyabilir; `users` tablosunda yalnız `id, role, full_name, is_active, is_demo, created_at` sütunlarını görür (şifre özeti, e-posta ve 2FA sırrı **görünmez**).
- Model eğitimi için hazır veri: `research.timeline` (zaman serisi, tek tablo), `research.glucose_readings`, `research.brfss_survey`, `research.food_images` + `research.food_classes` (fotoğraf modeli).
- `quality_flag IS NULL` ile süzün (sensör tabanı ve olanaksız değerler işaretli).

## 9. Şema değişikliği

Şema değişiklikleri artık **Flyway** ile yapılıyor (`DiaMate/src/main/resources/db/migration`). Bu paketin kurduğu şema **V1** (başlangıç) sayılır; backend açılırken Flyway `V2__...sql`, `V3__...sql` dosyalarını sırayla bir kez uygular ve `flyway_schema_history` tablosuna yazar. Bu klasördeki SQL dosyaları **değiştirilmez**: yeni bir ortam önce `install_mac.sh` ile V1'e kurulur, sonra backend'in ilk açılışında migration'lar uygulanır. `06_app_schema.sql` ile `reset_and_run_all.sql` yeni bir ortam kurmak içindir, üretim verisinin üstünde çalıştırılmamalıdır (siler).

**V2 (users):** `full_name` yerine `first_name` + `last_name` (`full_name` artık `GENERATED ALWAYS AS (first_name || ' ' || last_name)`, yazılamaz), `date_of_birth` ve `gender` (`FEMALE`/`MALE`/`OTHER`) `users`'a eklendi ve `patient_profiles.date_of_birth` / `sex` buraya taşındı. `v_patient_overview` artık `sex` yerine `gender` döner. Bu dokümandaki ve `DATA_DICTIONARY.md` / `ERD.md` içindeki `users` / `patient_profiles` açıklamaları V1 halini anlatır.
